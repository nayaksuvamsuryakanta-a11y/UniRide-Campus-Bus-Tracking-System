# Codebase Technical Summary

Line references below refer to the repository files as inspected for this document.

## 1. Overview

UniRide is a campus transit dashboard for Dr. Harisingh Gour Vishwavidyalaya in Sagar. The server is a Flask application backed by SQLite; the browser UI is a single HTML page styled with CSS and uses Leaflet for the map. Buses and routes are demo data, and bus movement is generated by an in-process simulation thread.

The application is assembled as follows:

```text
Browser requests GET /
  -> Flask renders templates/index.html
  -> browser loads style.css, app.js, Leaflet, and map tiles
  -> app.js fetches route, notification, and schedule data
  -> app.js opens GET /api/buses/stream (SSE)

Flask API handlers <-> get_db() <-> SQLite (routes, stops, buses, schedules, notifications)
        ^                                      ^
        |                                      |
        +-- GPS/admin/demo writes -------------+
                                               |
app import -> init_db() -> start_simulation() -> daemon worker ticks every 3 sec
                                               |
                          commit state -> notify_bus_update() -> SSE event stream wakes browsers

If EventSource is unavailable or errors/times out, app.js polls buses and notifications every 3 sec.
```

The application configures logging and Flask-Limiter, initializes the schema and seed data at import time, and starts the worker in `app.py` (lines 18–47). `wsgi.py` exposes the same Flask `app` to Gunicorn (lines 1–4); the included container runs one Gunicorn worker with 16 request threads (Dockerfile lines 17–18).

## 3. API surface

All `/api/` routes are subject to Flask-Limiter’s default `60 per minute` limit (app.py lines 27–33). Authentication descriptions below are route-level checks; GET routes are public unless stated otherwise. JSON error responses use `{"status":"error","error":"..."}` where applicable.

| Method and path | Auth | Request body / query | Response shape and behavior |
|---|---|---|---|
| `GET /` | none | none | Renders the dashboard HTML (`app.py:49–52`). |
| `GET /api/buses` | none | none | `status`, `count`, `timestamp`, and `buses` array containing bus columns plus route name/code/color (`app.py:54–79`). |
| `GET /api/buses/stream` | none | none | `text/event-stream`; initial `buses` and `notifications` named events, then both after update notifications; 15-second keep-alive comments (`app.py:101–130`). |
| `POST /api/buses/<bus_id>/location` | `GPS_UPDATE_TOKEN` via `X-Update-Token` | JSON object; required `lat`, `lng`; optional `speed_mph`, `heading`, `delay_minutes`, `eta_minutes`, `status`, `next_stop_name` (`app.py:132–180`). | Success: `status`, `message`, `bus_id`, `lat`, `lng`, `updated_at`; validation/auth/not-found failures are JSON errors (`app.py:182–241`). |
| `POST /api/demo/buses/<bus_id>/location` | `ADMIN_TOKEN` via `X-Admin-Token`; then shared GPS validation | Same telemetry object as direct GPS update (`app.py:244–252`). | Same success/error contract as direct GPS route. This path forwards the server’s configured/generated GPS token internally. |
| `GET /api/routes` | none | none | `status`, `routes`; each active route includes decoded `waypoints` and ordered `stops` (`app.py:254–283`). |

Token checks use `hmac.compare_digest`. For admin routes, an unset `ADMIN_TOKEN` returns 503; a missing or wrong header returns 401 (for example app.py lines 453–463). GPS updates require the token even when it was generated at process start. Auth is intentionally different by route class: read routes and the read-only simulation status endpoint are public, GPS ingestion uses its own token, and demo/mutation routes use `ADMIN_TOKEN`.

There is a client mismatch: the notification dismiss button calls the POST route without adding `X-Admin-Token` (`static/js/app.js:1111–1115`), while the server requires it (`app.py:379–383`).

The schema is created in `database.py:109–187`. Primary keys are `INTEGER PRIMARY KEY AUTOINCREMENT`; no explicit secondary indexes are created. `get_db()` enables SQLite foreign keys on each normal connection (`database.py:17–23`); reset temporarily disables them only while dropping the tables, then turns them back on (`database.py:101–107`).

Nullable relationship fields (`schedules.bus_id`, `notifications.bus_id`, `notifications.route_id`) allow unassociated schedules/alerts and may be intentional. Descriptive `routes.description` and `buses.next_stop_name` are also optional. Many operational fields have defaults but no `NOT NULL` constraint, including route frequency/active flag, bus telemetry/status values, and schedule/notification status flags; SQLite therefore permits explicit NULL despite those defaults. The application often assumes values are present, so constraints could be tightened if NULL is not a supported state.

Potential indexing gap: lookups repeatedly use `stops.route_id` ordered by `stop_order` (app.py lines 268–275; simulation.py lines 63–67), `buses.route_id` (app.py lines 65–70), schedule `route_id`/`bus_id` (app.py lines 293–305; simulation.py lines 199–232), and notifications `is_active`/`bus_id` (app.py lines 87–94; simulation.py lines 192–197). No indexes are declared for those fields; only primary-key and unique constraints create indexes (schema above).

## 5. Background simulation

`simulation.py` sets a 3-second interval, a worker-enabled flag, a single simulation lock, and a condition/version counter (`simulation.py:24–30`). On each tick `step_simulation_once` reads routes, stops, and buses; advances each valid bus to the next waypoint modulo the route length; calculates the heading to the following waypoint; derives `speed_mph` from distance moved during the tick; then writes current coordinates, waypoint index, heading, speed, nearest-stop name, ETA, and timestamp (`simulation.py:53–133`). The “next stop” is selected as the geographically closest stop, not by the route’s stop order (`simulation.py:96–116`).

After commit, a tick increments the update version and wakes all condition waiters (`simulation.py:131–133`, `33–51`). The SSE stream waits on that version and emits updated bus and notification snapshots (`app.py:104–120`). Delay changes use the same lock and database, changing bus status/delay, alert activity, and schedule status (`simulation.py:168–237`).

The worker catches/logs exceptions and continues, sleeping after each iteration (`simulation.py:135–144`). `start_simulation` starts a daemon thread if needed; pause/resume only flips `_sim_running` (`simulation.py:146–166`). `app.py` starts it as part of module import (`app.py:43–47`), and the demo toggle is admin-protected (`app.py:432–446`). There is no join/shutdown method; pausing does not interrupt a currently executing tick or the sleep.

## 6. Client-server communication

The app loads route, notification, and schedule data using `fetch` during initialization (`static/js/app.js:203–235`). For live fleet updates, `startLiveUpdates` prefers `EventSource('/api/buses/stream')`; it parses named `buses` and `notifications` events. If EventSource is absent, errors, or no bus event arrives within five seconds, it closes the stream and starts polling (`static/js/app.js:1284–1339`). Polling fetches `/api/buses` and `/api/notifications` immediately and then every 3 seconds (`static/js/app.js:1342–1351`). `closeLiveUpdates` closes the event source and clears timers before unload (`static/js/app.js:1353–1367`).

The client state tracks routes, buses, schedules, notifications, map markers/polylines, selected route/bus, language and audience, simulation display state, connection mode, and live-update timers (`static/js/app.js:8–31`). Language, audience, route filter, and large-text preference use localStorage; the admin token is cached in sessionStorage (`static/js/app.js:1372–1379`).

## 9. Known issues / rough edges

- **Notification dismiss cannot authenticate from the current UI.** `dismissNotification` sends a bare POST and does not use the session admin token helper (`static/js/app.js:1111–1115`), while the route now rejects missing `X-Admin-Token` (`app.py:379–383`). The UI ignores the HTTP status and then refreshes notifications, so a click can appear to do nothing.
- **Other dynamic dashboard HTML still interpolates API/database strings into HTML.** Notification title/message use `escapeNotificationText` (`static/js/app.js:186–198`, `1081–1090`), but bus cards and Leaflet popups interpolate fields such as `bus_number`, `status`, `next_stop_name`, route names/codes/colors, and driver names into HTML (`static/js/app.js:794–812`, `836–877`, `894–971`). Authenticated GPS input can set `status` and `next_stop_name` (`app.py:178–180`, `216–229`), so these are possible stored-markup surfaces if a trusted GPS token is misused or compromised.
- **Simulation starts during module import.** This is convenient for the included one-worker Gunicorn setup, but a Flask development reloader can import the module in more than one process and risk multiple simulation workers writing the same database (`app.py:43–47`, `465–471`; `simulation.py:146–152`).
- **Delay schedule synchronization updates status but not estimated time.** Delay handling updates schedules’ `status` values but does not modify `estimated_time` (`simulation.py:227–232`), despite UI/demo wording implying timetable synchronization (template `index.html:201–209`).
- **“Speed” can be unusually high because each tick jumps a full waypoint.** It now correctly reports distance per fixed 3-second tick (`simulation.py:28`, `81–95`), but the waypoint spacing was generated by six coordinate subdivisions between road keypoints (`database.py:36–58`, `233–236`). The resulting speed may not represent plausible campus driving; this is a simulation-model limitation rather than a mismatch between displayed and computed speed.
- **No explicit indexes for common foreign-key/filter columns.** See the data-model section; the seeded dataset is small, but query cost grows as data grows.
- **The dashboard contains a disabled route/stop search input.** It is marked `disabled` in the template (`index.html:93–96`); no search behavior is implemented in `app.js`.
- **The stylesheet has successive theme overrides.** It declares a base design and then repeated root/token/component overrides later in the same file (`style.css:5–38`, `1953–1974`, `2193–2217`), which makes the effective style harder to determine from an early rule alone.
